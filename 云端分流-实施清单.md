**四处设计调整**

1. **传输改为 SSH 直传，不用对象存储**（§5 / N04）。本地 `transport=scp`、云端 `transport=file`，共享 `/opt/qwent/inbox`；两端零公网入站端口。`SftpTransport` 最终用系统 `ssh`/`scp` 命令而非 paramiko —— 本机 paramiko 2.8.x 只发 SHA-1 `ssh-rsa`，服务器已禁用，显式 pkey 仍认证失败。大分片走 scp 单文件 + 重试 + `.tmp` 原子改名，支持中断续传。
2. **微信"不扫码"= 凭据迁移**。官方渠道只有扫码登录，`pairing` 是批准联系人而非登录。把本地 `openclaw-weixin/accounts/*`（token / sync buf / context tokens）scp 到服务器 `~/.openclaw/`，配合 `merge_openclaw.py`（默认 dry-run、只合并、不改主模型、保留 QQ 渠道）即可无需再扫码。凭据失效才退回本地扫码。
3. **不生成 ChatTrace stub 目录**。改为 `main.py` 顶层 `try: import chattrace ... except ImportError: from cloud_stub import ...`，bundle 里直接带 `cloud_stub.py`，少一层生成逻辑。
4. **云端 `import app.main` 的 Linux 兼容性已实测通过**（`QWENT_CLOUD=1` → `IS_CLOUD=True`）：`paths.py` 云端返回占位目录、`qq_local.py` 给 `ctypes.wintypes` 最小类型替身、`main._on_startup` 跳过 13 个本机线程、`FRONTEND.is_dir()` 已有保护所以不挂载前端。

## 0.2 上线结果与验收记录（2026-11-09 17:02）

**部署结果**：`152.136.96.212:/opt/qwent`，systemd `qwent-cloud`（enabled + active），只监听 `127.0.0.1:8721`；服务器原有 8000 端口服务、OpenClaw QQ Bot（1903204947）均未受影响。整库基线 64 分片（1.67 GB 密文 / 4,253,863,936 B 原始）恢复成功，`quick_check=ok`，`epoch=e6d043208da4`。

**数据一致性**：18 张白名单表逐一与本地对账，`schema_sig=dd4f5ef48d47955b46a52180f9f48a59` 两端一致；追平后 16 张表零差异，`message` / `vec_done` 仅差 1~2 行（本地实时写入的瞬时差，由 10 分钟增量补平）。增量包 `seq=1..4` 全部按序应用，`applied_seq=4`、`error=""`。

**实施中新发现并修复的 4 个问题**

1. **基线水位窗口丢数据**：首版 `baseline()` 在上传完成后才装 CDC trigger 并 `prune(MAX(lsn))`，导致 16:08 快照 → 16:25 装 trigger 之间写入的 48 条消息既不在快照里、也没有 CDC 记录。修复：快照**之前**先装 trigger；快照完成立刻把 `lsn_to` 写进 manifest；只 prune 到该水位，之后的变更留给第一个增量包；`cloud_apply.restore_baseline()` 把 `applied_lsn` 对齐 `manifest.lsn_to`。旧格式 manifest 无 `lsn_to` 时退回 0（不 prune）。存量差异用正常 CDC 记录 + `sync_now()` 补偿，未重做 1.67 GB 基线。
2. **重做基线时按 size 误跳分片**：`_enc` 用随机 nonce，新快照密文必变；改为只有「复用同一批本地分片」时才允许按大小跳过，新基线一律全量重传。
3. **10 分钟自动同步没挂上**：`main._on_startup()` 本地分支缺 `cloud_sync_local.start()`，只有手动按钮可用。已补 `start()` / `stop()`，循环内部按 `cloud.enabled` + `auto` 自判；`POST /api/cloud/config` 也会即时启停。
4. **接管没停本机微信网关**：`effective_bot_conf()` 只关了本机 qqbot，同一凭据双端在线会互踢。已在 `main._on_startup()` 和 `POST /api/cloud/config` 里，于 `cloud.enabled && takeover_bots` 时调用 `_kill_gateways()`。切换后实测本机 18789 端口已释放。

**微信免扫码上线的三个坑（已写进 `cloud/README.md`）**

- 插件 **2.4.8 与 OpenClaw core 2026.10.9 不兼容**（`ERR_PACKAGE_PATH_NOT_EXPORTED: ./plugin-sdk/infra-runtime`）；升级到 **2.4.10** 后正常。本地正常组合是 core 2026.6.35 + 插件 2.4.10。
- 合并进第二个 agent 后必须声明 `agents.ownership="explicit"`，否则 `openclaw config validate` 失败、Gateway 起不来，连带原有 QQ Bot 一起下线。模板 `openclaw.json.example` 已带该字段。
- `ownership="explicit"` 下没有隐式路由，必须 `openclaw agents bind --agent qwent --bind "openclaw-weixin:<accountId>"`，否则微信消息会落到默认 `main`/deepseek。

## 1. 设计决策（已定，实施时不再摇摆）

| ID  | 决策                                                                                                                                                 |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | **不 fork 问答代码**。云端 bundle 由打包脚本从 `backend/app/` 白名单拷贝同一份源码 + 生成 3 个 stub，`IS_CLOUD` 环境变量控制分支，保证「功能与当前一致」由构建过程自动保证。                                 |
| D2  | **不整库复制、不做页级 patch**。采用逻辑 CDC：白名单表建 AFTER trigger 写 `_cloud_cdc(lsn)`，10 分钟导出变更行。理由：能选择订阅哪些表，云端会话数据不会被覆盖；页级复制无法排除写入。                               |
| D3  | **增量包只带逻辑行，不带 FTS/vec 影子行**。云端按同一套建索引逻辑从行重建 `message_fts` 并用本地 bge 模型补 `msg_vec_p`。10 分钟几十条，开销可忽略。                                                 |
| D4  | **首次基线整库传**（4.25 GB，zstd 分片），保证向量索引与本地字节级一致、免去云端重建 130 万条向量。精简基线（只传逻辑行 + 云端重建）作为备选，不默认启用。                                                          |
| D5  | **私有对象存储中转**，本地主动上传、云端轮询 manifest 拉取。两端都不需要公网入站端口、域名、TLS 证书。P0 联调先用 `file://` 本地目录后端。                                                              |
| D6  | **云端不拆库**。`db()` 保持不变（改它要动全项目 SQL）；基线恢复前把云端 `ai_qa/ai_session/qq_message/qq_conv` 导出 JSON，恢复后导回。日常 apply 只做行级 UPSERT，绝不整库覆盖。                       |
| D7  | **云端带 `models/bge-small-zh`**（~95 MB）保住向量检索。默认沿用 `transformers+torch`；可选导出 ONNX 版省约 1 GB 内存，属优化项不入 P0。                                             |
| D8  | **Gateway 与助手同机部署在云端**，`127.0.0.1` 与写死的 `baseUrl` 均不用改。仅当 P0 微信渠道 Linux POC 失败、走「Gateway 留本机 + 指向云端」退路时，才参数化 `baseUrl`。                            |
| D9  | **接管用统一函数** `cloud_conf.effective_bot_conf()`：`IS_CLOUD=False` 且开关开启时强制本地 `qqbot.enabled=False`、停本地 Gateway，但**保留 `agent_api.api_key`**（云端用同一把钥匙）。 |
| D10 | **开关默认关闭**。所有改动都是 `if not IS_CLOUD` 分支或新增文件，本地原有路径零变化，可整体 revert。                                                                                  |

## 10. 接管 / 回退状态机

| `cloud.enabled` | `takeover_bots` | 本地 qqbot          | 本地 Gateway            | 云端 qqbot | 云端 Gateway | 本地 Web UI    |
| --------------- | --------------- | ----------------- | --------------------- | -------- | ---------- | ------------ |
| false           | *               | 按 `qqbot.enabled` | 按 `agent_api.enabled` | 停        | 停          | 本地实时库        |
| true            | true            | **强制停**           | **强制停（保留 key）**       | 启        | 启          | 本地实时库        |
| true            | false           | 按原配置              | 按原配置                  | 停        | 停          | 本地实时库（仅数据上云） |

`cloud_conf.effective_bot_conf()` 伪代码：

```python
def effective_bot_conf(conf: dict) -> dict:
    c = {k: dict(v) if isinstance(v, dict) else v for k, v in conf.items()}
    if IS_CLOUD:
        return c                                  # 云端按原配置启动两个通道
    cloud = c.get("cloud") or {}
    if cloud.get("enabled") and cloud.get("takeover_bots", True):
        c.setdefault("qqbot", {})["enabled"] = False
        c["_gateway_owned_by"] = "cloud"         # /api/openclaw/toggle 据此只停进程
    return c
```

**切换顺序（开启）**：配置保存 → `/api/cloud/test` 通过 → 首次基线 → 云端 restore + health OK → `effective_bot_conf` 生效、本地 qqbot/Gateway 下线 → 云端 `apply_config` 上线 → 进入 10 分钟增量。**必须等云端 health OK 才下线本地**，避免出现两边都不答的空窗。

**关闭**：云端两个通道停 → 本地恢复原配置 → 增量同步可继续或暂停（默认继续但 `takeover_bots=false` 语义）。
